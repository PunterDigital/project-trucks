# ProjectTrucks — notes for Claude

Local Euro Truck Simulator 2 delivery tracker, **Windows only** (ETS2 telemetry needs Windows;
there is no macOS build since v0.1.0, whose `.dmg` stays on that release). Tauri 2 desktop app: React 19 + Vite + Tailwind v4 +
shadcn/ui frontend, Rust backend with SQLite via sqlx. Read `PLAN.md` (architecture) and
`CLAUDE_CODE_PLAN.md` (milestone tasks) before feature work; if they conflict, `PLAN.md` wins.

| What | Command |

checkout.

## E2E approach

Playwright drives the **real app binary** (not a dev server): `e2e/fixtures.ts` spawns
`src-tauri/target/{release,debug}/projecttrucks.exe` (or `PROJECTTRUCKS_EXE`) with
`PROJECTTRUCKS_E2E_CDP_PORT=<port>`. The app then builds its main window with
`--remote-debugging-port` (see `create_main_window` in `src-tauri/src/lib.rs`; the window is
`create: false` in `tauri.conf.json`), and the test connects with `chromium.connectOverCDP`.
WebView2's own `WEBVIEW2_*` env vars are ignored on GitHub's Windows runners, so don't switch back to
them.

E2E runs on Shay's PC, often while he plays ETS2 (Nov 14: test windows kept pulling focus from the game). With the
CDP port set, `create_main_window` builds the window `focused(false)` + `skip_taskbar(true)` and adds
`CalculateNativeWinOcclusion` to `--disable-features` plus `--disable-backgrounding-occluded-windows
--disable-renderer-backgrounding`, so a window under the game keeps rendering. Never call `bringToFront()` or focus the
window from a spec. That wasn't enough (#4712: three ~1 s grabs late in a run over Helldivers 2): tao clears its
"don't focus" marker right after creating the window, so a later style refresh re-shows it with `SW_SHOW`, and Windows
lets that through once the foreground lock timeout has passed with no keyboard/mouse input (controller play). So the
test window is also `focusable(false)` (`WS_EX_NOACTIVATE`) and gets a subclass (`src-tauri/src/e2e_window.rs`) that
adds `SWP_NOACTIVATE` to every position change, refuses mouse activation and, if activated anyway, hands the foreground
back to the window it came from. Never call `set_focus()` in test mode either: tao's `force_window_active` fakes an Alt
key press to steal the foreground. Check with `scripts/fg-logger.ps1` in the control repo during a full run.

Isolation: every test sets `PROJECTTRUCKS_DATA_DIR` (see `src-tauri/src/db/mod.rs`), which holds the
SQLite database and the WebView2 profile (`<dir>/webview`). Never run E2E without it: the default
data dir is Shay's real database at `%APPDATA%\co.shaypunter.projecttrucks\`.

Parallel (#4675): `fullyParallel`, 3 workers in CI, 2 locally (`PT_E2E_WORKERS=<n>` overrides). Nothing may be
shared between tests: the CDP port is `9300 + workerIndex` (specs that relaunch the app use the same), the Hub and
update mocks listen on port 0, fake game folders come from `mkdtemp`. A new spec with a fixed port or a fixed temp
path breaks this. The remaining `waitForTimeout`s are "nothing happens" checks (no sync after unlink, no link after
cancel, capture stays off/waiting, a dismissed prompt stays away); everything else waits on what the page shows.

## CI / release

- `ci.yml`: ubuntu frontend typecheck/lint/unit tests/build; windows fmt/clippy/test, installers, E2E against the release
  binary. Both job names are required checks on `main`: keep them unchanged. A `changes` job runs
  `scripts/is-version-bump.mjs <base> <head>` (merge-base diff): when only version lines in `package.json`,
  `tauri.conf.json`, `Cargo.toml`, the app's own `Cargo.lock` entry and `CHANGELOG.md` change, the Windows job is
  skipped (Shay, Nov 14: release bumps shouldn't burn a full Windows run; the tag's `release.yml` builds anyway).
  Keep release PRs to exactly those edits, or they get the full run.
- `release.yml` on `v*` tags: creates the release with generated notes, `tauri-action` (v1) uploads the
  Windows `_x64-setup.exe` / `.msi`, then a job verifies both exist. tauri-action v1 rewrites the name and body
  of an existing release from its inputs, so the first job passes the generated notes on as `releaseBody`.
- Version lives in `package.json`, `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` (+ `Cargo.lock`):
  bump all of them in the release commit.

## Dependency updates

Tauri's npm packages (`@tauri-apps/*`) and Rust crates (`tauri`, `tauri-*`) must stay on the same
minor version, or `tauri build` fails with "Found version mismatched Tauri packages". Dependabot
opens npm and cargo PRs separately, so `.github/dependabot.yml` ignores Tauri's minor/patch bumps
(majors still come as PRs) and the weekly maintenance run bumps both sides in one PR:
`pnpm update '@tauri-apps/*' --latest` (stay on 2.x), then in `src-tauri`
`cargo update -p tauri -p tauri-build -p tauri-plugin-opener`, check the `tauri` crate and
`@tauri-apps/api` share a minor, and run the full CI locally. The ignore also hides Tauri security
updates, so check `pnpm audit` and the repo's Dependabot alerts for Tauri in the same run.

## Quirks

- CSP lives in `tauri.conf.json` (`app.security.csp`). Tauri adds script hashes to it only when it
  bundles `dist/`: `tauri dev` loads Vite's `http://localhost:1420` with **no CSP at all**, so check
  CSP changes against a release binary (`pnpm tauri build --no-bundle` + `pnpm test:e2e`). The E2E
  fixture fails any test with a console error, which is how a violation shows up. `style-src` needs
  `'unsafe-inline'` for sonner's runtime `<style>` tag; Tauri doesn't add a nonce there, so it works.
  Anything new that loads remote content (fonts, images, `fetch`) needs the CSP widened.

- react-hooks 7 flags `setState` called synchronously in an effect. Reset state when an input
  changes by comparing with the previous value during render (`Jobs.tsx` page reset,
  `JobDetail.tsx`), and derive "loading" from which request the last response belongs to.
- E2E can seed data through `window.__TAURI_INTERNALS__.invoke("create_job", …)` in
  `page.evaluate` instead of filling the form many times (`e2e/app.spec.ts` pagination test).
- The ETS2 telemetry plugin DLLs under `assets/telemetry-plugin/` are third-party binaries. Their
  SHA-256s are in that folder's README; re-check them if the files change.
- Telemetry (M2) reads a memory-mapped file from the plugin, which is why the app is Windows-only.
- The bundled `ets2-telemetry-server.dll` is a prebuilt binary that writes plugin **revision 9**, though the headers and
  source snapshot say 10 (same rev1–rev4 layout). Until #4607 `SUPPORTED_REVISIONS` was `[10]`, so every real frame
  failed ("unsupported telemetry plugin revision 9", logged at debug only) and the status stayed "not connected"; replay
  fixtures never go through `from_bytes`, so E2E couldn't see it. `testdata/plugin-rev9-frame.bin` is a frame captured
  from the real game. To check against a running game: the app in a throwaway profile with auto-capture on, then
  `get_telemetry_status` over CDP (`RUST_LOG=projecttrucks_lib=debug` shows read errors).
- On this PC Steam finds the real ETS2 (`D:\SteamLibrary\...`) and the plugin is installed there, so `detect_on_first_run`
  fills the ETS2 folder in E2E profiles too and `telemetry.spec.ts` "suggests the plugin…" fails locally (no prompt).
  CI has no ETS2; it passes there.
- Migrations: sqlx stores each applied migration's SHA-384 and refuses a database whose stored checksum differs from
  the embedded file. Git checked `0001_init.sql` out as CRLF on GitHub's Windows runner and LF locally, so a database
  made by a local build crashed the released app in `setup()` before any window (#4601). `.gitattributes` pins
  `src-tauri/migrations/*.sql` to LF, and `db::migrate` first rewrites a stored checksum that matches the other line
  endings (`repair_line_ending_checksums`; a real edit still fails). Never edit an applied migration: add a new one.
  A failed `setup()` now shows a MessageBox with the error chain (`show_startup_error` in `lib.rs`, skipped when the
  E2E CDP port is set). In a release build stderr goes nowhere, so to see the log run the exe from a shell with
  `PROJECTTRUCKS_DATA_DIR` pointing at a copy of the database, never the real one.
- A copied-in `src-tauri/target` from another path breaks the build ("failed to read plugin
  permissions … app_hide.toml"): delete `src-tauri/target`.
- Telemetry replay: set `PROJECTTRUCKS_TELEMETRY_REPLAY=<fixture.json>` (and optionally
  `PROJECTTRUCKS_TELEMETRY_REPLAY_INTERVAL_MS`) and the background task replays recorded snapshots
  instead of reading ETS2 (`src-tauri/src/telemetry/replay.rs`, `e2e/telemetry.spec.ts`). Each sample's
  `t` is virtual seconds, so a fixture can cross the 5 minute idle timeout in one step. The task runs
  from `lib.rs` `setup()` and only polls (or replays) while the `auto_capture` setting is on (default off, a
  `watch` channel in `settings.rs`): E2E specs that need a replay switch it on in Settings first. Turning it off
  resets the pipeline, so a drive in progress is dropped.
- Settings live in the `settings` key/value table (`src-tauri/src/settings.rs`); the ETS2 folder is found
  through Steam (registry `SteamPath`, `libraryfolders.vdf`, `appmanifest_227300.acf`). The frontend keeps them
  in `src/lib/settings.ts`; `formatKm` follows the km/mi setting (stored values stay km).
- The telemetry plugin installer (`src-tauri/src/plugin_installer.rs`) copies the bundled x64 DLL, a Tauri resource
  (`bundle.resources`, copied next to the exe by the build script, so `--no-bundle` release binaries have it too), into
  `<ets2>/bin/win_x64/plugins`. A folder "looks like ETS2" when `bin/win_x64/eurotrucks2.exe` exists, which is how the
  E2E builds a fake game folder in a temp dir. Installed/outdated is a SHA-256 comparison; a different DLL is kept as `.bak`.
- Plugin switch (#4619): the app ships RenCloud's `scs-telemetry.dll` v1.12.1 (`assets/telemetry-plugin/scs-telemetry/`,
  revision 12, mapping `Local\SCSTelemetry`, 32 KB), decoded by `telemetry/struct_scs.rs` at fixed offsets (the header
  pads its struct into zones with documented start offsets; the test re-derives each field from its zone start). The
  reader (`TelemetryReader::open_any`) prefers that mapping and falls back to Funbit's `Local\Ets2TelemetryServer`
  (`struct_v.rs`), so an install that hasn't pressed Update keeps recording; the connect is logged with the plugin.
  RenCloud keeps the last job's strings in the frame after it ends, so a job exists only while `special_b.onJob` is set
  (cleared on the game's delivered/cancelled events). Installing also removes our old `ets2-telemetry-server.dll` (only
  if its SHA-256 is the one we shipped, `OLD_DLL_SHA`) and its `.bak`, and the status says Outdated while either is
  there. The DLL has no version resource, so a different `scs-telemetry.dll` is replaced (kept as `.bak`), not
  compared. Other trackers' DLLs (Shay has `ETSSharedMemoryMapPlugin64v2.dll`) are never touched. RenCloud's
  gameplay events are read since #4756 (next bullet). Checked against the real game on Nov 15 with both plugins loaded at once
  (`PROJECTTRUCKS_LIVE_TELEMETRY=1` or `=funbit` on the `live_game` test, `PROJECTTRUCKS_LIVE_TELEMETRY_DUMP=<file>`
  saves the raw frame): every shared field matched except the truck names (Funbit said make id `scs`, model `STD`;
  RenCloud says `volvo` / `FH4`, so jobs recorded before and after the switch show as two trucks) and the deadline.
  Fixtures: `testdata/scs-rev12-free-roam-frame.bin`, `scs-rev12-job-frame.bin`, and a whole recorded delivery
  (`scs-recorded-delivery.json`, a replay fixture: 662 frames at 1 Hz thinned to 180 samples that keep every
  pause/job/trailer edge and gameplay event; `struct_scs::recorded`). In that delivery the game paused on the results
  screen, `onJob` cleared 3 s later while still paused (0.11 km left) together with the "delivered" event, then
  autopark unhitched the trailer; since #4756 the state machine records the delivery on that event frame (before, on
  the first unpaused frame after the results screen). The recording was made with a throwaway read-only PowerShell recorder (`MemoryMappedFile.OpenExisting`
  with Read rights, one `[i64 ms][7560 B scs][2048 B funbit]` record per second); `recording_to_replay` (opt-in
  test) turns such a file into a replay fixture.
- Gameplay events (#4756): RenCloud's plugin flips a `special_b` flag with XOR on each game event (`jobDelivered`,
  `jobCancelled`, `fined`, `tollgate`, `ferry`, `train`; `scs_telemetry.cpp` V.1.12.1) and fills the `gameplay_*` values
  in the same frame, so any change between two frames is one event. `struct_scs::EventTracker` (inside the reader, so
  a reconnect starts a new baseline; the first frame is never an event) turns flips into `TelemetrySnapshot.events`
  (`GameplayEvent`, `#[serde(default)]`, so replay fixtures can carry them too). At delivery the plugin also clears
  `onJob` **and the job strings and income**, so an event can't name its job: the state machine finishes whatever job
  it tracks, before the paused early return (the results screen pauses the game), and remembers it as `delivered` in
  case a torn frame still shows it. A restored job not yet confirmed by an unpaused frame is left to the old rules,
  which stay as the fallback for Funbit's plugin and missed events. The job row gets the game's figures
  (`jobs.game_revenue`, `earned_xp`, `cargo_damage`, `game_distance_km`, `auto_park`, `auto_load`,
  `cancel_penalty`; migration 0006) through `commands::expenses::set_game_result`. Tolls,
  fines and fares go on `JobInProgress.expenses` (saved with the job, so a restart keeps them) and into `expenses`
  with the job's id when it's written (`ON DELETE CASCADE`), or straight away with no job id in free roam. Stats:
  income is `COALESCE(game_revenue, declared_income)`; `PeriodStats.costs` = expenses by `occurred_at` + cancel
  penalties (Dashboard Income card's second line). CSV: eight columns appended. The recorded-delivery fixture was
  regenerated from Shay's raw recording with events (toll 19 at 238 s; delivered: revenue 4,478, XP 320, 229 km,
  auto-park + auto-load). E2E: `e2e/gameplay-events.spec.ts` (ends on the results screen). Hub sync (#5227): `JobPayload` sends `game_revenue`, `earned_xp`,
  `cargo_damage`, `cancel_penalty` and `costs` (`expenses::job_costs`: the job's expenses summed; null for a job with
  no game figures and no expenses, 0 for a scs-telemetry job that paid nothing); migration 0007 adds the four job columns
  to the outbox trigger. The Hub counts `game_revenue` as income when present. E2E: the second test in
  `gameplay-events.spec.ts` links to the stub Hub (`e2e/stub-hub.ts`, shared with `hub.spec.ts`) and checks what it got.
- No-deadline jobs: an external-market job has delivery time `u32::MAX`. Funbit passes it on as -1, which read as a
  date before the game's clock, so every such delivery was recorded **Late**. Both decoders now read it as no
  deadline (`deadline: None`, never late).
- E2E teardown on Windows: `rmSync` of the data dir can fail (EPERM) while WebView2 still holds a file, more often
  with parallel workers. Since #4675 the `dataDir` fixture only warns, and `e2e/global-teardown.ts` removes this run's
  leftover `projecttrucks-e2e-*` folders (made after `global-setup.ts` noted the start) once every app has exited.
- Recorded (telemetry) jobs are sanity-checked in `insert_job_row` (`sanity_flag` in `commands/jobs.rs`): average speed over
  150 km/h or distance under 1 km sets `flagged` + `flag_reason`; manual entries are never auto-flagged.
  Speed is per **in-game** hour (#4771): ETS2's odometer counts game km, ~19 per real km on roads (Shay's recorded
  delivery: 123.8 km in 11 real minutes = 663 km/h, 104 game minutes = 71 km/h), so distance / real time flagged every
  real job. `JobInProgress.started_game_time` + the completing frame's clock give `jobs.game_duration_min`; every
  recorded job must also stay under `MAX_PLAUSIBLE_REAL_KMH` (3,000 km per real hour, same as the Hub). Without a game
  time (jobs from before 0.11) the average is per real hour and the job page shows "—". Migration 0004 cleared the old
  speed-only flags that pass the real-time limit. Fuel used and damage delta are summed frame by frame on the running
  job (`JobWear`: refuels, repairs and a detached trailer don't count; saved with the job at most every 30 s when only
  they change); damage = truck chassis + trailer wear gained.
  E2E replays without a `gameTime` get a game clock that runs with the virtual seconds (`scenarios.spec.ts` `push`). The Jobs list and
  job page show a "Flagged" badge. `e2e/scenarios.spec.ts` replays a whole shift (cancel, on-time, ferry teleport, alt-tab gap,
  fast delivery) with a `Shift` builder; the first 1.2 km of a job are driven before the job is seen, so distances are 10.8 not 12.
- Recorded cancels (#2513) get a job row with status `CANCELLED` linked to their `JOB`/`CANCELLED` session (also when cancelled
  while parked), so they show in Jobs. Stats count only `DELIVERED`/`LATE` as deliveries and income, the km stay in the
  session, and `insert_job_row` never sanity-flags a cancel (one dropped right after pickup is under 1 km on purpose).
  The first real-game test (Nov 14) recorded the cancel as a cancelled session as expected: paused on the frame before the
  job vanished. Shay's live database isn't visible from Claude's shell here (`%APPDATA%` showed a stale May copy): ask him
  for a Settings → Backup file instead.
- Owned trailers (#4734): the bundled plugin (`ets2-telemetry.cpp` frame callback) clears the job fields only when the
  trailer is **unhitched** with under 500 m of route left. An owned trailer stays hitched after the drop-off, so the
  delivered job stays in the frame for good, and before the fix the app kept "driving" it (Shay's Poznań → Málaga
  delivery, Nov 14: the Hub's live status still said on the job, 2,346 km, no route). The state machine now ends a job
  when its route advisor was under `Config::arrival_km` (2 km) and then reads 0 on two unpaused samples in a row, and
  ignores that stale job (`delivered`) until the frame shows a different one or none. Within 2 km a vanished job is
  also delivered even if paused (the results screen pauses the game). A disconnect resets the arrival tracking, since
  a reloaded game can show an empty route for a moment. E2E: `e2e/owned-trailer.spec.ts`.
- Restart mid-delivery (#4730): the pipeline saves the state machine's active job (`JobInProgress`, serde) and the
  delivered-but-still-in-the-frame job as JSON in the settings table (`telemetry_active_job`,
  `telemetry_delivered_job`) whenever they change, and `Pipeline::restored` loads them when the runner starts. A
  restored job is kept only if the game's first **unpaused** frame shows the same job (`same_job`); otherwise it's
  dropped silently (no row: it ended while the app was closed) and the frame's job starts fresh. Switching
  auto-capture off still drops the drive in progress and clears both keys (`Pipeline::forget`). A bad saved value is
  ignored with a warning. E2E: `e2e/restart-mid-job.spec.ts` launches twice on one data dir with two replays.
- Dashboard (M3.1, `src/routes/Dashboard.tsx`, `commands/stats.rs`): `get_dashboard_stats` takes the viewer's UTC offset
  (`-getTimezoneOffset()`), so "this month" and the 30-day series follow local days; tests pin `now` through
  `DashboardQuery`. Distances follow the rollup rules (sessions carry recorded km, a manual job its own; cancelled
  manual jobs still count km, not deliveries or income). Charts are recharts with `var(--chart-*)` fills; they draw
  nothing in a zero-size container, so the chart boxes have fixed heights. Stat cards carry
  `data-testid="stat-card"` + `data-label` for E2E (`e2e/dashboard.spec.ts`).
- Job in progress (#4620, `src/components/JobInProgress.tsx` on the Dashboard, `telemetry/current_job.rs`): each tick the
  runner builds a `CurrentJob` from the state machine's active job (start odometer) and the latest frame (odometer, route
  advisor) and emits `telemetry:job` (object or `null`) when it changes; `get_current_job` answers a page opened later.
  Completion = driven / (driven + route km left), `None` without a route (the plugin writes 0). The route-advisor numbers
  are `navigation_distance` (m) and `navigation_time` (**game** seconds: the real frame had 808 km / 24.3 h with a ferry)
  in rev4; `JobSnapshot.route_distance_km` / `route_time_minutes` are `#[serde(default)]` so older replay fixtures still
  parse. E2E: `e2e/job-in-progress.spec.ts`.
- Truck page (M3.2, `src/routes/TruckDetail.tsx`): `get_truck_stats(id, query)` returns `None` for an unknown id, else the
  truck row plus a lifetime `PeriodStats` scoped to the truck (`TruckScope` in `commands/stats.rs` pushes
  `truck_make = ? AND truck_model = ?` into the same queries the dashboard uses, so the two can't drift), the job count,
  the mean of the job rows' own `distance_km` and the 30-day series. `JobFilter`/`SessionFilter` take `truckMake` +
  `truckModel` (send both) for the "Jobs" and "All sessions" tabs; the shared table lives in `src/components/JobsTable.tsx`
  (with `Pager`). Tabs are radix via the `radix-ui` umbrella package (`src/components/ui/tabs.tsx`, written by hand, no
  new dependency). E2E: `e2e/truck-detail.spec.ts` seeds two trucks and checks the page against the Trucks list and the
  Dashboard; `data-testid="truck-jobs"` / `"truck-sessions"` / `"session-kind"`.
- Export / backup (M3.3, `commands/export.rs`, Settings "Your data"): `export_jobs_csv(path)` writes RFC 4180 CSV
  (`CSV_COLUMNS` order, CRLF, hand-rolled quoting, no csv crate) and returns the job count; `backup_database(path)` runs
  `VACUUM INTO` on the live pool after deleting any existing target (VACUUM INTO refuses a non-empty file). The native
  save dialog is `tauri-plugin-dialog` (crate + `@tauri-apps/plugin-dialog`, keep both on the same minor; capability
  `dialog:allow-save`), wrapped as `api.pickSavePath`. Playwright can't drive the dialog, so `e2e/data.spec.ts` calls the
  commands with paths in the test's `dataDir` and checks the files from Node (`node:sqlite` opens the backup).
- Loading / empty / error states (M3.4): no "Loading…" text anywhere. While a route's first request is in flight it shows
  a shape from `src/components/Skeletons.tsx` (`TableSkeleton`, `StatsPageSkeleton`, `JobDetailSkeleton`, …; each root has
  `data-testid="skeleton"` + `aria-busy`, so E2E waits for `getByTestId("skeleton")` to reach count 0). Every "nothing here"
  box is `src/components/EmptyState.tsx` (`data-testid="empty-state"`, `compact` for a list inside a page) with its next
  action as buttons: "Log a job" / "Log your first job manually" and "Turn on auto-capture" (→ `/settings`). A failed load
  is `src/components/LoadError.tsx` (`role="alert"`, `data-testid="load-error"`, "Try again" bumps an `attempt` counter in
  the effect deps or the request key); failures of user actions stay sonner toasts. `src/components/ErrorBoundary.tsx`
  wraps the whole tree in `main.tsx`: a render error shows "Something went wrong" + the message + Reload
  (`window.location.reload()`); its unit test (`ErrorBoundary.test.tsx`) runs in jsdom (`// @vitest-environment jsdom`,
  `vitest.config.ts` includes `*.test.tsx`). `e2e/empty-states.spec.ts` covers the fresh-install states, not-found pages
  and the filtered-empty "Clear filters" action.
- First-launch prompt (`src/components/PluginPrompt.tsx`, shown under the header except on `/settings`): when the plugin
  is missing or outdated it offers Install/Update with the saved ETS2 folder. "Not now" stores the bundled DLL's SHA-256
  (`plugin_prompt_dismissed` setting, `PluginStatus.bundledSha`), so it only returns when the app ships a different plugin.
  The other E2E specs run with no ETS2 folder, so the prompt is on screen in them; don't give it a button named like
  "Install plugin" (`telemetry.spec.ts` selects that on the Settings page).
- App icon (M4.1): the source is `assets/icon/projecttrucks.svg`. Regenerate every size with
  `pnpm tauri icon assets/icon/projecttrucks.svg`, then delete the `android/` and `ios/` folders it drops into
  `src-tauri/icons` (no mobile targets). `scripts/check-win-icon.ps1` compares the icon Windows extracts from an `.exe`
  with `32x32.png` (System.Drawing can't decode the PNG-compressed frames in `tauri icon`'s `.ico`, and the NSIS
  installer only carries the icon through `bundle.windows.nsis.installerIcon`); CI runs it on the release exe and the NSIS installer after `tauri build`, so the Tauri
  default icon can't come back unnoticed. `bundle.publisher` / `longDescription` / `copyright` in `tauri.conf.json`
  feed the installer's Add/Remove Programs entry and the exe's version resource.
- One-click updates (#3354, `src-tauri/src/updater.rs`, `src/components/UpdateBanner.tsx`, Settings "Updates"): no Tauri
  updater plugin (it needs an update-signing key as a repo secret). On launch (setting `check_updates`, default on) and
  from "Check now" the Rust side reads GitHub's `releases/latest` JSON (reqwest with `native-tls`, i.e. schannel:

- ProjectTrucks Hub sync (#4634, `src-tauri/src/hub/`, `src/components/HubSettings.tsx`, Settings → "ProjectTrucks Hub"):
  links the app to a Hub account (https://project-trucks.shaypunter.co.uk, the Laravel app in `../project-trucks-hub`; API
  contract in its `docs/api.md`) with the device-code flow: `hub_link_start` asks for a code, shows it, opens the approval page
  and polls until the driver approves. The token lives in Windows Credential Manager (`token.rs`, generic credential
  `ProjectTrucks/hub-token`, plain `windows-sys` calls, no keyring crate); test profiles keep it in `<data dir>/hub-token`.
  Migration `0002_hub_sync.sql` adds `hub_outbox` + `hub_jobs` and **triggers on `jobs`** that queue inserts, edits (of the
  synced columns only, never `notes`) and deletes while the `hub_linked` setting is `'true'`, so every write path is covered
  without calling the sync code; jobs from before linking go only through "Sync history". `run_sync` drains the outbox every
  3 s (deletes, then batches of 100; a 422 batch is retried job by job and a job refused 5 times is parked as "refused";
  network errors back off 10 s → 5 min). A 401 anywhere = unlinked on the website: token and queue are dropped. Results clear
  only the outbox row with the `queued_at` they were sent for, so an edit mid-send stays queued. Status goes out as
  `hub:status` (`src/lib/hub.ts`). Live status (#4635, `hub/live.rs`): the runner publishes each tick to a watch channel;

- Theme (#4658, Settings → Theme: Light / Dark / System, default System): a setting like the others (`theme` key,
