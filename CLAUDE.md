# ProjectTrucks — notes for Claude

Local Euro Truck Simulator 2 delivery tracker, **Windows only** (ETS2 telemetry needs Windows;
there is no macOS build since v0.1.0, whose `.dmg` stays on that release). Tauri 2 desktop app: React 19 + Vite + Tailwind v4 +
shadcn/ui frontend, Rust backend with SQLite via sqlx. Read `PLAN.md` (architecture) and
`CLAUDE_CODE_PLAN.md` (milestone tasks) before feature work; if they conflict, `PLAN.md` wins.

## Commands

| What | Command |
|---|---|
| Install | `pnpm install` |
| Run the app | `pnpm tauri dev` |
| Frontend typecheck | `pnpm typecheck` (app + E2E sources) |
| Frontend lint | `pnpm lint` (ESLint flat config: typescript-eslint, react-hooks; `src/components/ui` is generated by shadcn and ignored) |
| Frontend unit tests | `pnpm test` (Vitest, `src/**/*.test.ts`; `vitest.config.ts`, separate from the Tauri `vite.config.ts`) |
| Frontend build | `pnpm build` |
| Rust format | `cd src-tauri && cargo fmt --check` |
| Rust lint | `cd src-tauri && cargo clippy --all-targets -- -D warnings` |
| Rust tests | `cd src-tauri && cargo test` (unit + `tests/m1_demo_flow.rs`, in-memory SQLite) |
| Release binary (for E2E) | `pnpm tauri build --no-bundle` |
| Installers | `pnpm tauri build` (Windows: NSIS `.exe` + `.msi`) |
| E2E | `pnpm test:e2e` (Windows only; needs the release or debug binary) |

`src-tauri`'s build script needs `dist/` to exist: run `pnpm build` before cargo commands on a fresh
checkout.

## E2E approach

Playwright drives the **real app binary** (not a dev server): `e2e/fixtures.ts` spawns
`src-tauri/target/{release,debug}/projecttrucks.exe` (or `PROJECTTRUCKS_EXE`) with
`PROJECTTRUCKS_E2E_CDP_PORT=<port>`. The app then builds its main window with
`--remote-debugging-port` (see `create_main_window` in `src-tauri/src/lib.rs`; the window is
`create: false` in `tauri.conf.json`), and the test connects with `chromium.connectOverCDP`.
WebView2's own `WEBVIEW2_*` env vars are ignored on GitHub's Windows runners, so don't switch back to
them.

Isolation: every test sets `PROJECTTRUCKS_DATA_DIR` (see `src-tauri/src/db/mod.rs`), which holds the
SQLite database and the WebView2 profile (`<dir>/webview`). Never run E2E without it: the default
data dir is Shay's real database at `%APPDATA%\co.shaypunter.projecttrucks\`.

## CI / release

- `ci.yml`: ubuntu frontend typecheck/lint/unit tests/build; windows fmt/clippy/test, installers, E2E against the release
  binary. Both job names are required checks on `main`: keep them unchanged.
- `release.yml` on `v*` tags: creates the release with generated notes, `tauri-action` (v1) uploads the
  Windows `_x64-setup.exe` / `.msi`, then a job verifies both exist. tauri-action v1 rewrites the name and body
  of an existing release from its inputs, so the first job passes the generated notes on as `releaseBody`.
- Version lives in `package.json`, `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` (+ `Cargo.lock`):
  bump all of them in the release commit.

## Dependency updates

Tauri's npm packages (`@tauri-apps/*`) and Rust crates (`tauri`, `tauri-*`) must stay on the same
minor version, or `tauri build` fails with "Found version mismatched Tauri packages". Dependabot
opens npm and cargo PRs separately, so `.github/dependabot.yml` ignores Tauri's minor/patch bumps
(majors still come as PRs) and the weekly maintenance run bumps both sides in one PR:
`pnpm update '@tauri-apps/*' --latest` (stay on 2.x), then in `src-tauri`
`cargo update -p tauri -p tauri-build -p tauri-plugin-opener`, check the `tauri` crate and
`@tauri-apps/api` share a minor, and run the full CI locally. The ignore also hides Tauri security
updates, so check `pnpm audit` and the repo's Dependabot alerts for Tauri in the same run.

## Quirks

- CSP lives in `tauri.conf.json` (`app.security.csp`). Tauri adds script hashes to it only when it
  bundles `dist/`: `tauri dev` loads Vite's `http://localhost:1420` with **no CSP at all**, so check
  CSP changes against a release binary (`pnpm tauri build --no-bundle` + `pnpm test:e2e`). The E2E
  fixture fails any test with a console error, which is how a violation shows up. `style-src` needs
  `'unsafe-inline'` for sonner's runtime `<style>` tag; Tauri doesn't add a nonce there, so it works.
  Anything new that loads remote content (fonts, images, `fetch`) needs the CSP widened.

- react-hooks 7 flags `setState` called synchronously in an effect. Reset state when an input
  changes by comparing with the previous value during render (`Jobs.tsx` page reset,
  `JobDetail.tsx`), and derive "loading" from which request the last response belongs to.
- E2E can seed data through `window.__TAURI_INTERNALS__.invoke("create_job", …)` in
  `page.evaluate` instead of filling the form many times (`e2e/app.spec.ts` pagination test).
- The ETS2 telemetry plugin DLLs under `assets/telemetry-plugin/` are third-party binaries. Their
  SHA-256s are in that folder's README; re-check them if the files change.
- Telemetry (M2) reads a memory-mapped file from the plugin, which is why the app is Windows-only.
- A copied-in `src-tauri/target` from another path breaks the build ("failed to read plugin
  permissions … app_hide.toml"): delete `src-tauri/target`.
- Telemetry replay: set `PROJECTTRUCKS_TELEMETRY_REPLAY=<fixture.json>` (and optionally
  `PROJECTTRUCKS_TELEMETRY_REPLAY_INTERVAL_MS`) and the background task replays recorded snapshots
  instead of reading ETS2 (`src-tauri/src/telemetry/replay.rs`, `e2e/telemetry.spec.ts`). Each sample's
  `t` is virtual seconds, so a fixture can cross the 5 minute idle timeout in one step. The task runs
  from `lib.rs` `setup()` and only polls (or replays) while the `auto_capture` setting is on (default off, a
  `watch` channel in `settings.rs`): E2E specs that need a replay switch it on in Settings first. Turning it off
  resets the pipeline, so a drive in progress is dropped.
- Settings live in the `settings` key/value table (`src-tauri/src/settings.rs`); the ETS2 folder is found
  through Steam (registry `SteamPath`, `libraryfolders.vdf`, `appmanifest_227300.acf`). The frontend keeps them
  in `src/lib/settings.ts`; `formatKm` follows the km/mi setting (stored values stay km).
- The telemetry plugin installer (`src-tauri/src/plugin_installer.rs`) copies the bundled x64 DLL, a Tauri resource
  (`bundle.resources`, copied next to the exe by the build script, so `--no-bundle` release binaries have it too), into
  `<ets2>/bin/win_x64/plugins`. A folder "looks like ETS2" when `bin/win_x64/eurotrucks2.exe` exists, which is how the
  E2E builds a fake game folder in a temp dir. Installed/outdated is a SHA-256 comparison; a different DLL is kept as `.bak`.
- E2E teardown can flake on Windows: `rmSync` of the data dir fails while WebView2 still holds a file. A rerun passes.
- Recorded (telemetry) jobs are sanity-checked in `insert_job_row` (`sanity_flag` in `commands/jobs.rs`): average speed over
  150 km/h or distance under 1 km sets `flagged` + `flag_reason`; manual entries are never auto-flagged. The Jobs list and
  job page show a "Flagged" badge. `e2e/scenarios.spec.ts` replays a whole shift (cancel, on-time, ferry teleport, alt-tab gap,
  fast delivery) with a `Shift` builder; the first 1.2 km of a job are driven before the job is seen, so distances are 10.8 not 12.
- Dashboard (M3.1, `src/routes/Dashboard.tsx`, `commands/stats.rs`): `get_dashboard_stats` takes the viewer's UTC offset
  (`-getTimezoneOffset()`), so "this month" and the 30-day series follow local days; tests pin `now` through
  `DashboardQuery`. Distances follow the rollup rules (sessions carry recorded km, a manual job its own; cancelled
  manual jobs still count km, not deliveries or income). Charts are recharts with `var(--chart-*)` fills; they draw
  nothing in a zero-size container, so the chart boxes have fixed heights. Stat cards carry
  `data-testid="stat-card"` + `data-label` for E2E (`e2e/dashboard.spec.ts`).
- Truck page (M3.2, `src/routes/TruckDetail.tsx`): `get_truck_stats(id, query)` returns `None` for an unknown id, else the
  truck row plus a lifetime `PeriodStats` scoped to the truck (`TruckScope` in `commands/stats.rs` pushes
  `truck_make = ? AND truck_model = ?` into the same queries the dashboard uses, so the two can't drift), the job count,
  the mean of the job rows' own `distance_km` and the 30-day series. `JobFilter`/`SessionFilter` take `truckMake` +
  `truckModel` (send both) for the "Jobs" and "All sessions" tabs; the shared table lives in `src/components/JobsTable.tsx`
  (with `Pager`). Tabs are radix via the `radix-ui` umbrella package (`src/components/ui/tabs.tsx`, written by hand, no
  new dependency). E2E: `e2e/truck-detail.spec.ts` seeds two trucks and checks the page against the Trucks list and the
  Dashboard; `data-testid="truck-jobs"` / `"truck-sessions"` / `"session-kind"`.
- Export / backup (M3.3, `commands/export.rs`, Settings "Your data"): `export_jobs_csv(path)` writes RFC 4180 CSV
  (`CSV_COLUMNS` order, CRLF, hand-rolled quoting, no csv crate) and returns the job count; `backup_database(path)` runs
  `VACUUM INTO` on the live pool after deleting any existing target (VACUUM INTO refuses a non-empty file). The native
  save dialog is `tauri-plugin-dialog` (crate + `@tauri-apps/plugin-dialog`, keep both on the same minor; capability
  `dialog:allow-save`), wrapped as `api.pickSavePath`. Playwright can't drive the dialog, so `e2e/data.spec.ts` calls the
  commands with paths in the test's `dataDir` and checks the files from Node (`node:sqlite` opens the backup).
- Loading / empty / error states (M3.4): no "Loading…" text anywhere. While a route's first request is in flight it shows
  a shape from `src/components/Skeletons.tsx` (`TableSkeleton`, `StatsPageSkeleton`, `JobDetailSkeleton`, …; each root has
  `data-testid="skeleton"` + `aria-busy`, so E2E waits for `getByTestId("skeleton")` to reach count 0). Every "nothing here"
  box is `src/components/EmptyState.tsx` (`data-testid="empty-state"`, `compact` for a list inside a page) with its next
  action as buttons: "Log a job" / "Log your first job manually" and "Turn on auto-capture" (→ `/settings`). A failed load
  is `src/components/LoadError.tsx` (`role="alert"`, `data-testid="load-error"`, "Try again" bumps an `attempt` counter in
  the effect deps or the request key); failures of user actions stay sonner toasts. `src/components/ErrorBoundary.tsx`
  wraps the whole tree in `main.tsx`: a render error shows "Something went wrong" + the message + Reload
  (`window.location.reload()`); its unit test (`ErrorBoundary.test.tsx`) runs in jsdom (`// @vitest-environment jsdom`,
  `vitest.config.ts` includes `*.test.tsx`). `e2e/empty-states.spec.ts` covers the fresh-install states, not-found pages
  and the filtered-empty "Clear filters" action.
- First-launch prompt (`src/components/PluginPrompt.tsx`, shown under the header except on `/settings`): when the plugin
  is missing or outdated it offers Install/Update with the saved ETS2 folder. "Not now" stores the bundled DLL's SHA-256
  (`plugin_prompt_dismissed` setting, `PluginStatus.bundledSha`), so it only returns when the app ships a different plugin.
  The other E2E specs run with no ETS2 folder, so the prompt is on screen in them; don't give it a button named like
  "Install plugin" (`telemetry.spec.ts` selects that on the Settings page).
