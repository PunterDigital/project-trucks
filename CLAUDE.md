# ProjectTrucks — notes for Claude

Local Euro Truck Simulator 2 delivery tracker, **Windows only** (ETS2 telemetry needs Windows;
there is no macOS build since v0.1.0, whose `.dmg` stays on that release). Tauri 2 desktop app: React 19 + Vite + Tailwind v4 +
shadcn/ui frontend, Rust backend with SQLite via sqlx. Read `PLAN.md` (architecture) and
`CLAUDE_CODE_PLAN.md` (milestone tasks) before feature work; if they conflict, `PLAN.md` wins.

## Commands

| What | Command |
|---|---|
| Install | `pnpm install` |
| Run the app | `pnpm tauri dev` |
| Frontend typecheck | `pnpm typecheck` (app + E2E sources) |
| Frontend lint | `pnpm lint` (ESLint flat config: typescript-eslint, react-hooks; `src/components/ui` is generated by shadcn and ignored) |
| Frontend unit tests | `pnpm test` (Vitest, `src/**/*.test.ts`; `vitest.config.ts`, separate from the Tauri `vite.config.ts`) |
| Frontend build | `pnpm build` |
| Rust format | `cd src-tauri && cargo fmt --check` |
| Rust lint | `cd src-tauri && cargo clippy --all-targets -- -D warnings` |
| Rust tests | `cd src-tauri && cargo test` (unit + `tests/m1_demo_flow.rs`, in-memory SQLite) |
| Release binary (for E2E) | `pnpm tauri build --no-bundle` |
| Installers | `pnpm tauri build` (Windows: NSIS `.exe` + `.msi`) |
| E2E | `pnpm test:e2e` (Windows only; needs the release or debug binary) |

`src-tauri`'s build script needs `dist/` to exist: run `pnpm build` before cargo commands on a fresh
checkout.

## E2E approach

Playwright drives the **real app binary** (not a dev server): `e2e/fixtures.ts` spawns
`src-tauri/target/{release,debug}/projecttrucks.exe` (or `PROJECTTRUCKS_EXE`) with
`PROJECTTRUCKS_E2E_CDP_PORT=<port>`. The app then builds its main window with
`--remote-debugging-port` (see `create_main_window` in `src-tauri/src/lib.rs`; the window is
`create: false` in `tauri.conf.json`), and the test connects with `chromium.connectOverCDP`.
WebView2's own `WEBVIEW2_*` env vars are ignored on GitHub's Windows runners, so don't switch back to
them.

Isolation: every test sets `PROJECTTRUCKS_DATA_DIR` (see `src-tauri/src/db/mod.rs`), which holds the
SQLite database and the WebView2 profile (`<dir>/webview`). Never run E2E without it: the default
data dir is Shay's real database at `%APPDATA%\co.shaypunter.projecttrucks\`.

## CI / release

- `ci.yml`: ubuntu frontend typecheck/lint/unit tests/build; windows fmt/clippy/test, installers, E2E against the release
  binary. Both job names are required checks on `main`: keep them unchanged.
- `release.yml` on `v*` tags: creates the release with generated notes, `tauri-action` uploads the
  Windows `_x64-setup.exe` / `.msi`, then a job verifies both exist.
- Version lives in `package.json`, `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` (+ `Cargo.lock`):
  bump all of them in the release commit.

## Quirks

- CSP lives in `tauri.conf.json` (`app.security.csp`). Tauri adds script hashes to it only when it
  bundles `dist/`: `tauri dev` loads Vite's `http://localhost:1420` with **no CSP at all**, so check
  CSP changes against a release binary (`pnpm tauri build --no-bundle` + `pnpm test:e2e`). The E2E
  fixture fails any test with a console error, which is how a violation shows up. `style-src` needs
  `'unsafe-inline'` for sonner's runtime `<style>` tag; Tauri doesn't add a nonce there, so it works.
  Anything new that loads remote content (fonts, images, `fetch`) needs the CSP widened.

- react-hooks 7 flags `setState` called synchronously in an effect. Reset state when an input
  changes by comparing with the previous value during render (`Jobs.tsx` page reset,
  `JobDetail.tsx`), and derive "loading" from which request the last response belongs to.
- E2E can seed data through `window.__TAURI_INTERNALS__.invoke("create_job", …)` in
  `page.evaluate` instead of filling the form many times (`e2e/app.spec.ts` pagination test).
- The ETS2 telemetry plugin DLLs under `assets/telemetry-plugin/` are third-party binaries. Their
  SHA-256s are in that folder's README; re-check them if the files change.
- Telemetry (M2) reads a memory-mapped file from the plugin, which is why the app is Windows-only.
- A copied-in `src-tauri/target` from another path breaks the build ("failed to read plugin
  permissions … app_hide.toml"): delete `src-tauri/target`.
- Telemetry replay: set `PROJECTTRUCKS_TELEMETRY_REPLAY=<fixture.json>` (and optionally
  `PROJECTTRUCKS_TELEMETRY_REPLAY_INTERVAL_MS`) and the background task replays recorded snapshots
  instead of reading ETS2 (`src-tauri/src/telemetry/replay.rs`, `e2e/telemetry.spec.ts`). Each sample's
  `t` is virtual seconds, so a fixture can cross the 5 minute idle timeout in one step. The task runs
  from `lib.rs` `setup()` and only polls (or replays) while the `auto_capture` setting is on (default off, a
  `watch` channel in `settings.rs`): E2E specs that need a replay switch it on in Settings first. Turning it off
  resets the pipeline, so a drive in progress is dropped.
- Settings live in the `settings` key/value table (`src-tauri/src/settings.rs`); the ETS2 folder is found
  through Steam (registry `SteamPath`, `libraryfolders.vdf`, `appmanifest_227300.acf`). The frontend keeps them
  in `src/lib/settings.ts`; `formatKm` follows the km/mi setting (stored values stay km).
